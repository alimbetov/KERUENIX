# 66 — R0 vertical slice S0: RFQ Draft → agreement → Execution → POD

**Status: S0 proposed execution design; NO production implementation approval.** This document specifies the first complete customer-isolated business journey in KERUENIX. It does **not** implement or qualify binding transport contracts or claim that current services support these operations.

Baseline: Java 21 Spring Boot modular monolith + PostgreSQL/PostGIS + Liquibase; PostgreSQL Outbox/Inbox, FORCE RLS and account-level ABAC; no Redis, Kafka, second job engine, or standalone Worker in R0. Existing PR #3 is a **Foundation/Test-First Draft**; keep vertical-slice domain implementation in **separate future Draft PRs** after independent S2 reviews.

## Business outcome and demonstration

Two independent organizations (customer, carrier) and two CustomerAccounts within one provider/tenant can participate only within explicitly authorized relationships. A real user enters cargo, pickup/drop-off, time window and instructions; saves and reopens a draft; submits after a reviewed binding-policy gate; receives a carrier offer; accepts an offer with explicit authority; a transport execution is created; custody milestones and tracking are recorded; delivery is confirmed with Proof of Delivery (POD). The customer can then see a complete event history and **no data** of another customer.

The target demonstration uses actual REST handlers, DB records and audit/outbox effects. Test-only controllers, static grant registries and synthetic `audit_fact.subject_ref` cannot pass S4.

## Business terms and legal boundary

- **RFQ** = request for quotation. `DRAFT` is non-binding and may be edited with owner privileges; it is not a booking.
- `SUBMITTED` = request visible to authorized counterparties, **only after decision DEC-R0-03** defines what submission legally/operationally means. Until then POST submit remains `403`/fail-closed.
- **Offer / Quote** = carrier's versioned price, currency, services, capacity/validity and fulfillment terms. Quote creation and visibility are tenant/CustomerAccount/relationship scoped.
- **Agreement/Booking** = explicit acceptance of a specific active quote version by an actor with a verified scope and legally accepted terms. Never infer agreement from `DRAFT`, a tracking update, or automatic match.
- **Execution** = separately versioned transport operation, initialized once from confirmed agreement. Tracking milestones are observational and cannot independently create binding authority.
- **POD** = evidence of physical delivery and recipient acknowledgement; it cannot be generated by merely setting a shipment status. Requires evidence owner, time, immutable attachment reference and audit trail.
- **Financial posting/payments/settlement** explicitly OUT OF R0 vertical slice unless separately reviewed. Route costs may be recorded as non-settled estimated commercial data.

## Modules and allowed dependencies

| Module | Owns data/transitions | Port, not direct cross-module repository |
|---|---|---|
| Identity/Tenancy | Actor, organization membership, verified access context | `VerifiedActorScope`, DB-backed account+operation grants |
| CustomerAccount | Customer-provider relationship and visibility | `CustomerAccountAuthorization` |
| RFQ | Draft cargo snapshot, RFQ status/version, submission, idempotency | `RfqCommandPort`, `RfqReadPort` |
| Commercial | Carrier quote version, offer validity, terms, customer acceptance | `OfferCommandPort`, `AgreementPort` |
| Execution | One execution from confirmed agreement, transport plan, milestones | `ExecutionCommandPort` |
| Custody | Handovers, evidence, operator/recipient roles | `CustodyPort` |
| Tracking | Timestamped geospatial/operational observation, source provenance | `TrackingEventPort` |
| Documents / POD | Evidence metadata, immutable content address, integrity, recipient confirmation | `PodCommandPort`, `DocumentPort` |
| Platform | Transactional outbox/inbox, audit, RLS, idempotency plumbing | Authorized application services call generic transport |

Modules may consume typed published domain events through application ports and existing Outbox. No DB-level cross-module joins or direct internal repositories unless a reviewed architecture decision explicitly permits it.

## Lifecycle and invariant-driven transitions

| Step | Transition | Required invariants |
|---|---|---|
| 1 | `RFQ_DRAFT_CREATED` | Verified actor + tenant+account grant; cargo snapshot persisted atomically; exactly one idempotent draft per `(tenant,account,actor,key)`; no quote/booking |
| 2 | `DRAFT_UPDATED` | Same account, expected version, optimistic conflict, audit, no binding effects |
| 3 | `DRAFT → SUBMITTED` | DEC-R0-03, explicit current authority, valid cargo/origin/destination, once-only submission event; no payment |
| 4 | `OFFER_CREATED / OFFER_REVISED` | Authorized carrier relationship, quote version, price/currency validity, immutable accepted version |
| 5 | `OFFER_ACCEPTED → AGREEMENT_CONFIRMED` | Explicit customer acceptance and correct active quote version; expired/replaced offer fails; concurrent accept retries produce at most one agreement |
| 6 | `AGREEMENT_CONFIRMED → EXECUTION_PLANNED` | Unique execution per agreement, full linkage RFQ/offer/account/tenant, audit+outbox in same transaction |
| 7 | `EXECUTION_STARTED → IN_TRANSIT` | Driver/dispatcher role and transport assignment validated, custody/tracking history append-only |
| 8 | `ARRIVED → POD_SUBMITTED → POD_ACCEPTED` | Delivery actor/recipient authority verified; evidence digest + immutable reference; duplicate submission idempotent; missing evidence rejected |
| 9 | `EXECUTION_DELIVERED` | Only from accepted POD; no arbitrary status PATCH, audit + delivery event transactional |
| 10 | Read model | Customer sees own account only, including list/count/cursor/geo; no existence leak via 403/404 semantics decided in Security review |

**State changes happen through domain command handlers, not via untrusted event payload or direct DB status mutation.** All customer/account IDs supplied in request bodies are untrusted selectors; server resolves the actual authorized scope. JWT identity is necessary but never sufficient.

## Cross-cutting constraints

1. **PostgreSQL transaction:** aggregate/version change + audit + outbox commit or rollback together; outbox delivery itself at-least-once and receiver idempotent.
2. **Optimistic locking:** expected version for editing/transition; no lost update, double booking, double POD or duplicated execution under concurrent requests.
3. **Idempotency:** scope key by tenant+account+actor+operation; canonical request fingerprint; replay identical returns original result; same key with changed payload -> `409`. Key expiry and response replay policy to be approved.
4. **Security:** DB-primary grant on every protected command/read. Revoked grant and database outage fail closed. Same-tenant CustomerAccounts X and Y must not share data even though tenant RLS admits both at tenant level.
5. **Documents:** attachment referenced by server-issued upload/content ID, not arbitrary client URL; MIME/size/virus controls to be specified; digest verification and lifecycle/retention approved before attaching real personal information.
6. **Geography:** PostGIS SRID 4326, explicit lat/lon domain and validation; do not substitute direct great-circle distance for commercial road mileage without route provider.
7. **Evidence:** server times UTC with event time + recorded time; actor, source, provenance and immutable audit; corrections append new facts, not erase history.
8. **No hidden scope expansion:** Carrier quotes, recipient POD, and external publication require separate permission contexts; one actor's RFQ draft grant cannot authorize downstream transitions.

## R0 vertical-slice test-first gates (minimum executable scenarios)

| ID | S1 test to write *before* domain code | Expected outcome |
|---|---|---|
| VS-01 | Valid JWT + real primary DB customer grant creates Draft on real Postgres | `201`, DRAFT record, audit; no binding event |
| VS-02 | Same idempotency key/request replay and changed payload | Stable ID/body on replay, `409` on mismatch |
| VS-03 | X/Y accounts under same tenant, forged selector/body, missing/expired JWT | No cross-account data/events, fail closed |
| VS-04 | Revoke grant between two requests, and simulate grant-store outage | Second request denied, no write/outbox |
| VS-05 | Submit cannot occur before binding authority/DEC-R0-03 | Rejected until approved policy and handler |
| VS-06 | Two carriers, only permitted relationship can see/respond; revised/expired quote rejected | Correct per-account ACL and offer versions |
| VS-07 | Concurrent quote acceptance / retry / stale version | At most one accepted agreement and one execution |
| VS-08 | Execution command with invalid assignment or role, tracking from unknown source | No unauthorized state mutation |
| VS-09 | Custody pickup/handover/order wrong, replay, missing actor | Rejected or exactly-once logical custody effect |
| VS-10 | POD missing immutable evidence or recipient confirmation, duplicate POD | Rejected or idempotently accepted once |
| VS-11 | Complete flow: Draft → Agreement → Execution → accepted POD | Linked persistent IDs, audit + outbox; no hidden payment |
| VS-12 | Read/list/count/cursor/tracking under account X vs Y; one-connection Hikari reuse | Zero cross-account exposure or metadata leak |
| VS-13 | Crash before transaction commit and consumer commit before outbox ACK | Atomic rollback; replay exactly once logically |
| VS-14 | PostGIS invalid coordinates, geofence/route tolerance, no-authorization query | Validated, isolated, accuracy documented |

**Test topology:** JUnit + Spring Boot real handlers, PostgreSQL/PostGIS with Liquibase and non-privileged app/dispatcher roles, Testcontainers or dedicated CI service; separate negative tests for JWT, grants, concurrent writes, restart/retention and tampered document references. RED must fail on a named missing *behavior*, never only on missing Java symbol/compilation or test-only blanket deny. Require exact-SHA workflow evidence and all test counts.

- **DEC-VS-04:** geography validation, location privacy, route-distance source, audit retention.
