# 38 — KERUENIX R0: онлайн-подписание ЭЦП без платёжных механизмов

**Версия:** 1.1.0 · **Дата:** 2026-11-08 · **Статус:** `DESIGN PROPOSAL / НЕ РЕАЛИЗОВАНО / ДОГОВОРНО-ЮРИДИЧЕСКОЕ СОГЛАСОВАНИЕ ТРЕБУЕТСЯ`.

**Источник продуктового решения:** KERUENIX обеспечивает перевозку, договорные условия, доказательства и коммерческие цены; **не проводит и не отслеживает денежные платежи**. При необходимости юридически значимые документы подписываются **ЭЦП НУЦ РК через внешний пользовательский способ подписи**. [Машинный контракт](contracts/r0-scope-eds-signing.v1.json), [Roadmap](33-tdd-development-roadmap-v1.md), [BR-12](contracts/r0-blocker-decisions.v1.json).

## 1. Что остаётся в системе, а что исключается

| Остаётся в KERUENIX | Уходит во внешнюю бухгалтерию / банк |
|---|---|
| Версия коммерческого предложения, сумма, валюта, единицы | Приём платежей, переводы, банковские операции |
| Предлагаемая стоимость перевозчика, себестоимость, маржа | Платёжный шлюз, acquiring, payout, escrow |
| Подписанный договор, Quote, договорное изменение, перевозочное доказательство | `PaymentAllocation`, AR/AP бухгалтерские книги, сверка платежей |
| Нейтральная ссылка/идентификатор документа, оформленного внешней системой | Официальная ЭСФ/налоговый учёт и подписания в государственном сервисе, если они осуществляются там |
| Коммерческий отчёт «предложение/обязательства» без признаков оплаты | `PAID`, `SETTLED`, `REFUNDED`, возвраты и chargeback |

**Юридический эффект:** ЭЦП подтверждает конкретный подписанный документ/волю уполномоченной стороны, но **не свидетельствует об оплате**. Нельзя выводить `PAID` из факта подписания договора, ТТН или внутреннего согласования.

**Технически:** оставляем в каноническом списке 17 доменов `finance`, но его R0-функциональность — **Commercial Cost / Margin Report + External Accounting Document Reference**. Не создаём внутренние банковские адаптеры, PaymentTransaction, PaymentAllocation, счёт для проведения платежей или платёжный UI. Внешний идентификатор бухгалтерского документа — метаданные, не бухгалтерское/банковское состояние.

## 2. Архитектура ЭЦП — один технический порт

```text
Customer / Provider / Carrier / Receiver UI
             │ request to sign exact document version
             ▼
          Domain owner
   Commercial / Booking / Execution
             │ immutable original + authority policy + expectedVersion
             ▼
    platform.signing (technical capability)
       ├─ SignRequestService
       ├─ immutable document snapshot and SHA-256
       ├─ SignerAuthorityVerifier
       ├─ NcaSignatureVerificationPort
       ├─ SignatureEvidenceStore (encrypted, immutable)
       └─ SigningAdapter
          ├─ NCALayer Web (FIRST)
          ├─ eGov Mobile QR (OPTIONAL, onboarding/provider)
          └─ verified signed original import (FALLBACK, legal approval)
             │ user device does signing, not backend
             ▼
    verify cryptography + NCA certificate + legal authority
             │ verified event + evidence reference
             ▼
 domain CAS: pending -> accepted/custody verified
       + audit + outbox in same PostgreSQL transaction
```

Это техническая возможность, **не 18-й бизнес-модуль**. Домены не импортируют чужие JPA/repository. ЭЦП-сервис не принимает решения за Commercial о Quote acceptance или за Execution о POD: только возвращает **проверенное доказательство**, по которому владелец домена выполняет свои business guards.

### Технологические варианты

| Вариант | Применение | Рекомендация |
|---|---|---|
| **NCALayer + НУЦ РК** | Веб-пользователь работает со своей ЭЦП локально; интерфейс открывает процесс подписи | **Первый вариант R0**. Требует реального интеграционного PoC браузера, формата подписи и серверного верификатора |
| **eGov Mobile QR / deep-link** | Мобильное подтверждение подписи, особенно удобно для внешнего клиента | **Опциональный адаптер**, только после проверки доступности API, договора с провайдером и юридического профиля |
| **Загрузка готового подписанного документа** | Контрагент подписал допустимым способом за пределами KERUENIX | Допустимый резервный маршрут **только после** проверки подписи, original bytes, срока, authority и документального профиля |

**Нельзя предполагать:** что QR в официальной ИС ЭСФ автоматически доступен для любого SaaS; что обычная аутентификация eGov Mobile означает подпись именно вашего документа; что браузерное `signatureValid=true` можно доверять.

## 3. Где подписывать, а где не усложнять

| Событие | Подпись по умолчанию | Обязательное условие |
|---|---|---|
| RFQ DRAFT / поиск / комментарий | Не нужна | Проверенные permission и scope |
| RFQ SUBMIT как **необязывающий запрос цены** | Не нужна, если согласован nonbinding профиль | Независимое право `customer:rfq:submit`, без создания договора |
| **Quote Acceptance** | **Да, рекомендуемый R0 профиль** | Уполномоченный подписант, точная `QuoteVersion`, одобренный юридический формат, BR-01/05 |
| **Carrier contractual commitment** | Да, когда договорный акт подписывается | Договор с перевозчиком, сторона/полномочие/период, BR-06 |
| Fleet Hold / GPS / внутреннее назначение | Нет | Не путать ресурсный hold с договорным обязательством |
| Материальные изменения договора | Да для требующих такой формы изменений | Новые `termsHash/version` и подтверждения требуемых сторон |
| CancellationRequest | По умолчанию нет | Сам запрос не прекращает договор; обязывающее соглашение подписывается при необходимости по BR-11 |
| Pickup/POD/ТТН/акт расхождений | По применимому юридическому профилю | Подписант, получатель, транспортная форма, оригинал; фото/хеш — не замена обязательному документу |
| Коммерческий отчет и ссылка на внешние бухгалтерские документы | Не нужна как платёжная подпись | Никаких `PAID` статусов/банковских интеграций |

## 4. Серверные инварианты подписи

1. **Freeze:** создать точное неизменяемое представление подписываемого документа (байты+content-type+schemaVersion+договорные стороны+QuoteVersion/DeliveryAttempt), вычислить hash на сервере. Запрос подписи всегда относится к конкретному `ownerId`, `tenant`, `customerAccount`, `expectedVersion`.
2. **Sign:** локальное приложение/подписывающий провайдер делает криптографическую подпись, закрытые ключи и пароль остаются у подписанта. Ни ЭЦП, ни пароль ключа не пересылаются как приватный ключ на backend.
3. **Verify:** сервер проверяет неизменяемые байты, алгоритм, открытый сертификат, цепочку НУЦ РК, срок действия/отзыв по юридически корректной процедуре, идентичность лица и его **полномочия подписывать от имени конкретного юрлица**. Подпись без полномочия не разрешает акцепт.
4. **Apply:** домен снова проверяет текущее состояние, версию, существующие права, срок Quote, коммерческие условия. Если исходная версия устарела, подпись не переносится автоматически на новую.
5. **Audit/Outbox:** сохранить оригинал, подпись и верификационное заключение с контрольными суммами; в одной БД-транзакции выполнить owner state change, audit, Outbox. Подпись внешнего сервиса и PostgreSQL физически не одна транзакция — нужны staged evidence, idempotency/reconciliation.
6. **Revocation:** последующее отключение пользователя не переписывает исторически подписанные документы; новая операция запрещена, актуальные полномочия и юридическая валидность проверяются отдельно.
7. **Privacy:** сертификаты содержат персональные сведения; применить минимизацию, разграничение доступа и хранение оригиналов по принятой legal retention policy. В логах нет ИИН, секретов, паролей, сырого тела договоров или закрытых ключей.

**Формат XML/CMS/PDF и криптографические библиотеки** выбираются в `PR-06S` после PoC с действующим SDK и серверным верификатором. **Для соответствия Цифровому кодексу РК ст. 50, 61, 62:** прежде чем предъявить кнопку подписи, показать подписанту именно оригинал, получить явное подтверждение, уведомить о подписи, обеспечить сохранение подписанного документа; проверять полномочия представителя через применимый официальный сервис и сделать подпись проверяемой извне при соблюдении конфиденциальности. Эти требования включены в SIG-14..18 и требуют legal/provider qualification.\n\nНельзя заранее утверждать, что подписанный произвольный PDF юридически эквивалентен утверждённой форме ТТН.

## 5. State machine и ошибки

```text
DRAFT -> FROZEN -> SIGN_REQUESTED -> SIGNED_UNVERIFIED -> VERIFIED
              |              |                  |          |
              |              +-- EXPIRED/CANCELLED             |
              +---------------- FAILED_VERIFICATION / DENIED   |
                                                        domain owner:
                                                ACCEPTED_BY_OWNER (CAS)
```

`SIGNED_UNVERIFIED` никогда не равно `ACCEPTED_BY_OWNER`. Сбой NCALayer, QR timeout, отсутствие доверенного источника сведений об отзыве, отсутствие полномочия, истечение сроков, подмена `termsHash`, неверная версия — запрет юридически значимого перехода с безопасным RFC 9457 кодом. У пользователя остаются варианты повторить подписание, обновить документ или обратиться к уполномоченному лицу.

## 6. TDD PR-06S — 18 обязательных спецификаций

| ID | Негативный/позитивный сценарий | Проверяемый результат |
|---|---|---|
| `SIG-01` | Подписан точный immutable документ | hash matches original, подписанное доказательство VERIFIED |
| `SIG-02` | Сертификат валиден, но подписант относится к другой компании | DENY, Quote не принимается |
| `SIG-03` | Просроченный/отозванный сертификат | DENY, без business Outbox |
| `SIG-04` | Подпись повторно применяют к другому QuoteVersion | DENY replay |
| `SIG-05` | Байты/условия изменены после FROZEN | DENY hash mismatch |
| `SIG-06` | Пользователь не завершил подписание до expiry | Осталось PENDING/EXPIRED, нет акцепта |
| `SIG-07` | Получена одна подпись дважды | Один owner transition/Outbox |
| `SIG-08` | Нажатие отмены заявки трактуют как подписание договора | Не допускается binding cancel |
| `SIG-09` | NCALayer/QR сервис недоступен | Без ложного ACCEPTED, безопасный retry |
| `SIG-10` | Сервер пытается получить/логировать приватный ключ или пароль | CI/security fail |
| `SIG-11` | Подписанный оригинал загружен из внешней процедуры | Криптография, полномочие, hash и origin проверяются |
| `SIG-12` | Подписание запрошено чужой CustomerOrg или отозванным пользователем | Нет signed artifacts или полномочий |
| `SIG-13` | Получатель подписывает акт о 8/10 CargoUnit | Акт immutable, Shipment остаётся PARTIAL |

| `SIG-14` | Exact-document preview, explicit confirmation, notification and ability to save signed original | Article 50 signer UX and consent tested |
| `SIG-15` | Проверка полномочий подписанта от имени юридического лица | Через применимый предусмотренный нормативными правилами сервис; при недоступности HOLD/DENY |
| `SIG-16` | Публично проверяемая подпись при сохранении конфиденциальности договора | Open verifier signature proof, не публичная раздача документа |
| `SIG-17` | Проверка через годы после restore/export | Подписанный оригинал переносим, доказательства времени/отзыва сохранены |
| `SIG-18` | Требуются подписи нескольких сторон и версия обновилась во время процесса | Частичная подпись не обязывает всех; superseded document не принят |

Тесты `SIG-01..18` **новые и не входят в 132 прежние бизнес-кейса**. Их существование в этом документе не означает прохождение. Для успешной квалификации необходимы реальные интеграционные/отказные проверки, а для юридического использования — утверждённый правовой профиль и проверка подписантов.

## 7. Изменение Roadmap и юридического согласования

- **Удалён из R0:** `PR-17S` — bank/ERP settlement, payment allocation, refund, pay state.
- **Новый `PR-06S`:** NCA signing adapter / NCALayer + independent server signature and authority validation. `PR-07` Quote Accept и `PR-13` custody legally binding evidence зависят от него.
- **`PR-17` упрощён:** только коммерческие цены/затраты, маржа и ссылка на внешний документ. Ни ЭСФ, ни AR/AP-проводок, ни платёжных состояний.
- **`PR-18/PR-19` больше не зависят** от банковского интеграционного PR. Полный R0 завершается корректной перевозкой, проверенными документами, коммерческой ценой и внешним accounting handoff.
- **`BR-12` остаётся ожидающим принятия** решения о сфере ответственности, но **его исходное требование обработки банковских оплат заменено** продуктовой границей без платежей.
- Старый тестовый банк сохраняется как история, но банковские positive cases помечаются `OUT_OF_SCOPE_R0`, не требуются для выпуска. Негативная проверка отсутствия платёжных эндпоинтов обязательна.

**Открытые вопросы перед PR-06S:**
1. В каких операциях конкретного договора требуется **ЭЦП**, а какие можно выполнять с audit/MFA, не нарушая обязательной формы?
2. Каков юридический способ проверки **полномочия представителя юридического лица** на момент подписи?
3. Какой формат подписанных данных/документов поддерживается NCALayer/QR-провайдером и как хранить оригинал для внешней проверки через годы?
4. Существуют ли доступный для KERUENIX договор/API и тестовый контур eGov QR? Если нет — NCALayer остаётся первым способом.

## 8. Первоисточники

- [Цифровой кодекс РК от 09.01.2026 №255-VIII, ст. 49, 61–62](https://old.adilet.zan.kz/rus/docs/K2600000255): законные условия ЭЦП, электронного документа и проверки полномочий.
- [НУЦ РК — NCALayer](https://pki.gov.kz/ru/ncalayer/): официальное средство работы с ЭЦП в веб-приложениях.
- [КГД о QR-подписании в ИС ЭСФ](https://kgd.gov.kz/ru/news/po-podpisaniyu-elektronnyh-dokumentov-posredstvom-skanirovaniya-qr-koda-1-134860): пример существующей интеграции **конкретного сервиса**, не доказательство открытого API для любого SaaS.
- [Пример API QR/eGov от SIGEX](https://egov4.sigex.kz/support/developers/api-egov-basic/): сторонний интегратор, доступность, юридический профиль и договор проверяются отдельно.

**Итог:** R0 не является платёжной системой. Подписанный документ и договорная ответственность — доказуемые, но не равнозначные банковскому расчёту. Статус `DESIGN PROPOSED` не означает готовность приложения или юридическое утверждение.
