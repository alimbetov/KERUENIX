# 28 — KERUENIX: модульная платформа как бизнес-продукт

**Идея:** один портативный Logistics Core и подключаемые бизнес-возможности без независимого микросервиса на каждую функцию.  
**Статус:** PROPOSED · **Дата:** 07.11.2026.

## Зачем

Небольшим перевозчикам нужен быстрый SaaS без собственного IT. Крупным логистическим компаниям — Dedicated или On-Prem, расширенные модули и интеграция с ERP. Оба клиента должны получать **одинаковую проверенную логику коммерческих обязательств, исполнения и прав**.

## Продуктовые пакеты (маркетинговая гипотеза)

| Пакет | Кому | Функции |
|---|---|---|
| Core TMS | Перевозчик/экспедитор | RFQ, Booking, Fleet, Trip, Cargo, Tracking, POD и Finance-lite |
| Partner Network | Экспедитор со сторонним транспортом | Подрядчики, догруз, trusted capacity offers и Rescue |
| Warehouse Hub | Склад/3PL | ASN, сканирование, SSCC, custody, WMS/YMS и cross-dock |
| International | Международная логистика | Утверждённые коды/документы/правила страны и вида транспорта |
| Intelligence | Флот с данными/сложными рейсами | Timefold планирование, прогнозы ETA/fuel, оптимизация |
| Enterprise | Крупный клиент | Dedicated/On-Prem, SSO, политики хранения и адаптеры ERP |

**Пакет не равен отдельной Java/JVM системе.** Возможности контролируются правами и соглашением; обязательные tenant/safety controls всегда работают.

## Технические варианты

**B (старт):** один Spring Boot runtime + Spring Modulith + PostgreSQL, концептуальная изоляция API/events/tables.  
**C (по сигналу):** Maven multi-module с тем же одним runtime; compile-time dependency isolation.  
**E (целевой вариант):** всё тот же core, плюс автономные GPS/routing/document workers по надёжному заданному контракту.  
**D (позже):** точечный выделенный микросервис, только когда измерены независимые нужды и восстановление.

Подробнее: [docs/13 — Options](../docs/13-modular-architecture-options-v1.md), [docs/14 — Delivery Blueprint](../docs/14-modular-delivery-blueprint.md).

## Бизнес-модули и принципы

`tenancy, commercial, fleet, cargo, booking, execution, tracking, documents, finance, compliance` — core; `recovery, warehouse, marketplace, optimization, regulatory, saas-control` — extensions/платформа. Это границы бизнес-ответственности, а не фиксированный список Spring Boot containers.

Нельзя делать новую «супер-сущность Order», которая прямо редактирует все модули. Модели заказа, грузовой партии, автомобиля и физического рейса имеют отдельные источники истины. Сквозные процессы координируются через публичные API/события и версии.

## Ключевые риски

1. «Сразу 16 микросервисов» → дорогая инфраструктура, неотлаженные распределённые транзакции.
2. «Один shared common JPA» → скрытые связи и невозможность выделить модуль.
3. «Feature flag отключает безопасность» → межклиентская утечка, незаконный запуск.
4. «Биржа = Booking» → двойные обязательства и фиктивная доступность.
5. «GPS = Shipment delivered» → ложное завершение.
6. «Все абстракции с первого дня» → нет реальной первой перевозки.

## Утверждение

Рекомендуется принять в качестве architecture baseline **B → E**, но официальное ADR остаётся предложением до согласования бизнес-ответственности Commercial/Finance, политики Tenant и пилота R0a. Далее создать контрактные/architecture tests на первом исполняемом коде.
