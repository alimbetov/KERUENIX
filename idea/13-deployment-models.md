# 13 — Две модели внедрения: KERUENIX Cloud и KERUENIX Enterprise

**Статус:** предлагаемое концептуальное решение · **Дата:** 07.11.2026

## Причина

Многие транспортные компании располагают автомобилями, водителями и заказами, но не имеют собственных серверов, DevOps и IT-отдела. Им нужен готовый SaaS с малым порогом входа. Другие компании обязаны или предпочитают запускать ПО в собственном дата-центре/частном облаке. **Одна кодовая база, один набор доменных контрактов, несколько способов развёртывания** закрывают обе группы без форка продукта.

Принцип: **multi-tenant — модель владения и авторизации данных, а pooled или dedicated — модель физического размещения. Эти понятия нельзя смешивать.**

## Продуктовые редакции

| Режим | Кто эксплуатирует | Изоляция | Клиентская задача |
|---|---|---|---|
| KERUENIX Cloud | Оператор SaaS | Общий runtime/БД, обязательные tenant_id + RLS + проверка доступа | Начать работу без собственной инфраструктуры |
| KERUENIX Dedicated Cloud | Оператор SaaS или MSP | Отдельный runtime и БД на клиента | Усиленная изоляция и специальные интеграции |
| KERUENIX Enterprise / On-Premises | Сам заказчик или подрядчик | Отдельный runtime, БД, файлы, секреты; один или несколько согласованных tenant | Контроль инфраструктуры и требований предприятия |

**Не создавать отдельную ветку продукта для Enterprise.** Вариации — через декларативную runtime-конфигурацию, лицензируемые возможности, инфраструктурные манифесты и адаптеры.

## Концептуальная архитектура

    SAME SOURCE / SAME RELEASE ARTIFACTS
                 |
           Deployment Profile
                 |
      +----------+--------------+
      |                         |
    SaaS pooled             Dedicated / On-prem
      |                         |
    Tenant A, B, C           Tenant A (или группа)
    Shared app              Isolated app
    Shared DB + RLS          Isolated DB + RLS
    Tenant-scoped files     Isolated object storage
    Quotas + metering       Local IAM, telemetry, custom APIs

Права доступа проверяются и в dedicated-режиме: отдельная инфраструктура не гарантирует безопасность между филиалами, юридическими лицами и ролями. `tenant_id` не нужно выбрасывать или подменять константой «GLOBAL».

## Deployment configuration (proposal)

Пример *концептуальных* параметров (не готовый application.yml):

    KERUENIX_DEPLOYMENT_MODE=SAAS_POOLED | DEDICATED | ON_PREM
    KERUENIX_TENANCY_STRATEGY=SHARED_SCHEMA_RLS | DEDICATED_DATABASE
    KERUENIX_DEFAULT_TENANT_ID=<provisioned server-side>
    KERUENIX_LICENSE_MODE=SUBSCRIPTION | ENTERPRISE
    KERUENIX_FEATURES=...
    KERUENIX_STORAGE_PROVIDER=S3
    KERUENIX_ROUTING_PROVIDER=...
    KERUENIX_TELEMATICS_PROVIDER=...

Секреты, KMS-ключи, URL БД, сертификаты, OIDC и учётные данные сторонних API предоставляются средой установки, не в исходном коде. Даже если в локальной инсталляции есть tenant по умолчанию, пользователь не должен получать право выбора произвольного tenant_id.

## Функции, общие для всех вариантов

- Orders, Shipments, Trips, RoutePlanVersion, Fuel, Cost, Fleet, Warehouse и единые правила расчётов.
- Tenant-bound RBAC/ABAC, аудит, наблюдаемость, управление заданиями и версионирование.
- Порты/адаптеры карт, трафика, GPS, ERP, WMS, ТРК/АЗС, RustFS/S3, оптимизаторов и ML.
- Обновления БД и API с совместимостью версий и проверками без кросс-клиентской утечки.
- Явная деградация при отключении трафика/GPS/ML и ограниченная работа без внешней сети.

## SaaS Cloud: onboarding и эксплуатация

1. Регистрация организации, подтверждение владения/администратора и создание tenant.
2. Выбор тарифа; применение квот пользователей, машин, GPS, заявок, API и вычислительных задач.
3. Приглашение сотрудников; роли и права; настройка собственных и привлечённых машин.
4. Данные компании изолированы в API, PostgreSQL/RLS, очередях, поиске, Redis, файлах, аналитике, логах и бэкапах.
5. Usage metering и биллинг отдельно от доменных данных; счётчик идемпотентный, лимиты прозрачные, перерасход контролируется.
6. Оповещения по проблемам сервиса, мониторинг, автоматические бэкапы и проверенное восстановление — обязанность SaaS-оператора.
7. Чёткие условия приостановки подписки, экспорт данных, удаление/retention и порядок выхода клиента из сервиса.

## Enterprise / On-Prem: эксплуатация и договор

- Контейнерная поставка: подписанные образы, `compose.yaml` для проверки и отдельный supported production deployment profile (например, Helm/Kubernetes только при обоснованной необходимости).
- Поддерживаемые версии PostgreSQL/PostGIS, объектного хранилища и Redis; health/readiness, миграции, совместимость, backup/restore runbook.
- Заказчик может использовать собственный OIDC/LDAP через поддерживаемый адаптер, свой GPS-провайдер, ERP и сеть.
- Явно описать разделение ответственности: обновления, патчи безопасности, наблюдаемость, доступ к техподдержке, инциденты, миграции, ключи и лицензии.
- Enterprise-лицензия должна поддерживать допустимую автономную работу, включая отсутствие доступа к SaaS control plane, без внезапного отключения перевозок.
- Конфиденциальные сведения и телеметрия заказчика не должны «звонить домой» без договора и согласованной телеметрии продукта.

## Межклиентское взаимодействие при разных развертываниях

Cloud Tenant A, Cloud Tenant B и On-Prem Tenant C могут участвовать в одной перевозке, но **не через прямые SQL joins, общие сессии или открытые БД**. Использовать отдельно согласованный межорганизационный API/асинхронный обмен с:
- scoped collaboration grants, подтверждением отношений и минимальными проекциями;
- версиями схем, идентификаторами отправлений, подписями/аутентификацией;
- идемпотентностью и восстановлением очередей при отключении on-prem сети;
- отзывом доступа, аудитом раскрываемых полей и сроками хранения.
В MVP можно ограничиться партнёрским порталом с ручным приглашением.

## Миграция клиента Cloud → Dedicated / On-Prem

Это нужно предусмотреть на уровне контрактов сразу, но автоматизировать позже:
1. Остановить новые записи для tenant и подготовить подтверждённую точку консистентности.
2. Экспортировать все tenant-owned данные, версии планов, документы, outbox, ссылки и конфигурацию.
3. Перенести секреты/интеграции только через безопасную процедуру, не как обычные поля экспорта.
4. Восстановить объекты, связи, номера, временные зоны и аудиторскую историю в выделенной среде.
5. Проверить целостность, количество сущностей, tenant isolation и идемпотентность повторного обмена.
6. Провести cutover/rollback с согласованным RPO/RTO и тестовым запуском.

## Экономическая модель (гипотезы)

- **Cloud:** подписка по компаниям/машинам/активным GPS/пользователям и отдельно измеряемые переменные расходы на маршруты/карты/инференцию.
- **Dedicated:** базовый контракт на выделенную инфраструктуру + эксплуатацию + интеграции.
- **Enterprise:** лицензия/поддержка + внедрение + опциональный SLA, интеграции и обновления.

Не вводить сложный usage-based billing до проверки себестоимости SaaS: карты/трафик, SMS, трекинг, хранилище и вычисления могут съесть маржу.

## Предварительные архитектурные решения

1. Один релиз приложения и одна доменная модель для Cloud/Dedicated/Enterprise.
2. Multi-tenancy обязателен на уровне домена и авторизации даже в single-tenant установке.
3. Стратегия хранения `shared schema + RLS` — стартовая для SaaS, отдельная БД — опция Enterprise.
4. Платформенные службы (provisioning, licensing, subscriptions) отделены от runtime логистики.
5. Подписка и доступность центрального SaaS не должны блокировать безопасность и сохранность локально выполняющихся рейсов.
6. Проверять экспорт/восстановление данных ещё в пилоте, а не после продажи Enterprise.

## Проверочные сценарии

- Две компании в Cloud видят только свои машины, цены, водителей и финансовые документы.
- Компания Cloud передаёт конкретное задание компании Enterprise; видимость ограничена разрешёнными milestone-данными.
- Предприятие на On-Prem работает во время потери интернет-связи с центральным облаком; внешние данные помечены устаревшими.
- Локальный администратор не может эскалировать доступ к данным другой компании/филиала.
- Одна и та же версия Logistics Core проходит интеграционные тесты для SaaS и isolated deployment.
- Экспорт тестового tenant и импорт в dedicated восстанавливают заказ, груз, маршрут, доказательство доставки и финансовый план/факт.
- Квоты одной SaaS-компании не блокируют работу соседних компаний.

## Следующие открытые вопросы

Нужны ли white-label домены, локализации KZ/RU/EN, отдельные юридические лица в tenant, конкретная модель SaaS-подписки, требования к региону хранения данных, офлайн-планирование, SLA/контракт поддержки и обязательные ERP/GPS-интеграции.
